# Interrupts

## What Is an Interrupt?

An interrupt is an event that alters a program's normal execution flow,
generated either by hardware devices or by the CPU itself. When one occurs,
the current flow is suspended, an interrupt handler runs, and execution then
resumes where it left off.

**Types:**

- **Synchronous** ("exceptions") — generated by executing an instruction;
  the processor detects a condition in the course of running it. A divide
  by zero or a system call are both exceptions.
- **Asynchronous** ("interrupts") — external events generated by I/O
  devices, e.g. a network card signaling that a packet has arrived.
- **Maskable** — most interrupts; the handler can be temporarily postponed.
- **Non-maskable** — a small set of critical interrupts that can't be
  disabled or postponed.

## Exceptions: Faults, Traps & Aborts

Exceptions come from two sources: **processor-detected** (fault, trap,
abort — raised when an abnormal condition is hit mid-instruction) and
**programmed** (`int n`).

| Term | Think of it as | Behavior |
|---|---|---|
| **Fault** | "Oops, fix and retry." | Reported *before* the faulting instruction completes; the saved return address points at the faulting instruction itself, so it can be corrected and re-executed (e.g. a page fault). |
| **Trap** | "All done, now call supervisor." | Reported *after* the instruction completes; the saved return address points at the *next* instruction (e.g. a debug trap, division by zero, illegal opcode, breakpoint). |
| **Abort** | "Too bad, can't continue." | A severe, generally non-recoverable fault. |

On ARM specifically, faults and traps break down further:

**Faults** (instruction aborts before it retires; if recoverable, the CPU
retries the instruction after the handler returns):

| Type | Exception class | Typical cause |
|---|---|---|
| Instruction Abort | Synchronous | Fetching from unmapped/inaccessible memory |
| Data Abort | Synchronous | Accessing invalid/unmapped memory (like a page fault) |
| Alignment Fault | Synchronous | Misaligned access on an architecture that requires alignment |
| Synchronous External Abort | SError | Memory system error detected during access |

**Traps** (the instruction completes successfully first; usually
intentional — system calls, debugging, exception-level transitions):

| Type | Exception class | Trigger |
|---|---|---|
| SVC (Supervisor Call) | Synchronous | EL0 (user) executes `svc #imm` to request a kernel service |
| HVC (Hypervisor Call) | Synchronous | A guest OS calls the hypervisor |
| SMC (Secure Monitor Call) | Synchronous | Normal ↔ Secure world communication (e.g. EL3 firmware like TF-A) |
| BRK (Breakpoint) | Synchronous | Debugging traps |

## Handling an Interrupt: ISR Basics

When the system takes an interrupt, it invokes the registered **interrupt
handler** (ISR), registered at compile time or boot. Once control reaches
the ISR, it: disables the IRQ line that fired, does its work quickly, then
re-enables that IRQ line.

The problem is step two — "do your work quickly" runs into real
constraints: what if the work takes too long? What if a higher-priority
interrupt arrives? What if the ISR needs to sleep? What if it deadlocks?
Different OSes and hardware solve this differently.

**In the Linux kernel, interrupt context cannot be preempted, sleep, or be
scheduled.** [[Kernel doc]](https://linux-kernel-labs.github.io/refs/heads/master/lectures/interrupts.html)
It's the driver author's responsibility to keep the ISR fast, non-sleeping,
and lock-free.

## Top Half vs. Bottom Half

The **top half** — the ISR itself — should only do work that meets one of
three conditions: it's time-sensitive, it's tied directly to the hardware
(e.g. must run before the IRQ line can be safely re-enabled), or it must not
be interrupted by another interrupt. **Everything else belongs in the
bottom half.**

"Later" in this context just means "not now" — bottom halves defer work to
whenever the system is next less busy and interrupts are enabled again, not
to any specific moment. Linux has accumulated several bottom-half
mechanisms over time; the four available today are **softirqs**, **tasklets**,
**work queues**, and **threaded IRQs** (plus kernel timers, which are also a
deferred-work mechanism). The older BH and task-queue interfaces still
exist but are effectively retired.

## The Evolution of Bottom Halves

### The Original BH Interface

The original "bottom half" (BH) mechanism gave the whole system a single
statically-created list of 32 BH slots. A top half marked which BH should
run by setting a bit in a 32-bit integer — but every BH was globally
synchronized, so no two could ever run at the same time, even on different
processors.

Think of it as a restaurant kitchen with exactly 32 trays for delayed
orders: a waiter (the top half) drops an order slip on a tray instead of
cooking it immediately, but no matter how many chefs (CPUs) are in the
kitchen, only one chef can cook at a time — tray #1 and tray #2 can never be
cooked simultaneously. Simple and easy to reason about, but a hard
bottleneck on SMP systems: limited to 32 slots, and zero parallelism no
matter how many CPUs were available.

**Task queues** were introduced later as both a way to defer work and a
would-be replacement for BH — but they still weren't lightweight enough for
performance-critical subsystems like networking.

During Linux 2.3, **softirqs and tasklets** replaced the BH system outright.
Softirqs are statically-defined bottom halves that can run concurrently on
any processor — even two softirqs of the *same* type can run at once on
different CPUs, as long as they're written to be reentrant. Tasklets are
built on top of softirqs: two *different* tasklets can run concurrently on
different processors, but two tasklets of the *same* type are always
serialized.

As of kernel 2.6 onward, the bottom-half mechanisms in active use are:

- Softirqs
- Tasklets
- Work queues

(Kernel timers also defer work; the old BH and task-queue interfaces remain
in the tree only for historical compatibility.)

### Softirqs

The number of softirqs is fixed at compile time — `NR_SOFTIRQS = 11` as of
kernel 6.15, stored in `struct softirq_action softirq_vec[NR_SOFTIRQS]`.

![1753247343375](/assets/images/notes/Linux_interrupt/1753247343375.png)

A registered softirq has to be explicitly marked pending before it runs —
**raising** it. Typically an interrupt handler raises its softirq right
before returning, and the softirq itself runs at a later, suitable point.
Pending softirqs get checked and executed in three places: on the return
path from a hardware interrupt, in the `ksoftirqd` kernel thread, or
anywhere in the kernel that explicitly checks for and runs pending softirqs
(the networking subsystem does this). Regardless of entry point, the actual
execution happens in `__do_softirq()`, invoked via `do_softirq()`.

Softirqs are reserved for the most timing-critical, highest-importance
bottom-half work in the system — currently only **networking** and **block
devices** use them directly, though kernel timers and tasklets are both
built on top of softirqs too. By convention, `HI_SOFTIRQ` is always the
first entry and `RCU_SOFTIRQ` always the last. A handler becomes runnable
once it's added to the softirq enum and registered via `open_softirq()`;
calling `raise_softirq()` (e.g. `raise_softirq(NET_TX_SOFTIRQ)`) marks it
pending for the next `do_softirq()` pass.

### Tasklets

Tasklets are themselves implemented as softirqs — specifically, all
tasklets are represented by one of two softirqs, `HI_SOFTIRQ` and
`TASKLET_SOFTIRQ`; the only difference is that `HI_SOFTIRQ`-based tasklets
run before `TASKLET_SOFTIRQ`-based ones.

![1753255235879](/assets/images/notes/Linux_interrupt/1753255235879.png)

Each `tasklet_struct` uses a C union so only one of its callback fields is
active at a time:

```c
if (t->use_callback)
    t->callback(t);
else
    t->func(t->data);
```

Its `state` field is one of `0`, `TASKLET_STATE_SCHED`, or
`TASKLET_STATE_RUN`; its `count` field acts as a reference count — nonzero
means disabled (won't run even if pending), zero means enabled.

Scheduled tasklets live in two per-processor linked lists of
`tasklet_struct`: `tasklet_vec` (regular) and `tasklet_hi_vec`
(high-priority). `tasklet_schedule()` / `tasklet_hi_schedule()` add a
tasklet to the right list and raise the corresponding softirq, so
`do_softirq()` runs it in the near future.

Practical rules for using tasklets:

- Can be allocated statically (`DECLARE_TASKLET(name, func, data)`) or
  dynamically (`tasklet_init(...)`).
- Like softirqs, tasklets **cannot sleep** — no semaphores, no blocking
  calls.
- They run with all interrupts enabled, so shared state still needs care.
- Scheduling the same tasklet twice before it's had a chance to run still
  only executes it once.
- As an optimization, a tasklet always runs on the CPU that scheduled it.

### ksoftirqd

Under heavy load (a busy network interface, say), softirqs can keep
re-triggering themselves. Handling every re-trigger immediately starves
user-space processes of CPU time — the system "feels frozen." Delaying
re-triggered softirqs until the next hardware interrupt instead protects
user-space responsiveness, but risks system services like networking
falling behind or failing.

Linux's answer: a per-CPU kernel thread, `ksoftirqd/n`, that runs at the
*lowest* scheduling priority. It won't preempt user programs, but it will
get CPU time whenever the system has spare cycles — including immediately
when the system goes idle. Concretely: each `ksoftirqd/n` checks for
pending softirqs, calls `do_softirq()` when there are any, keeps processing
if softirqs keep re-raising themselves, periodically checks whether it
should yield to something more important, and otherwise goes to sleep
(`TASK_INTERRUPTIBLE`) until woken again. The result is that both user-space
responsiveness and eventual completion of kernel-side work are preserved —
neither side is starved outright.

### Work Queues

Work queues defer work into a kernel thread that runs in **process
context** — meaning, unlike softirqs and tasklets, that deferred work *can*
sleep, use semaphores, allocate memory, or do disk I/O.

Linux ships default worker threads named `events/n` (one per CPU) that
handle deferred work from across the kernel, including drivers — most code
just uses these rather than spinning up a dedicated thread. A custom worker
thread is worth creating only when the work is heavy, long-running, or
performance-critical enough that it would otherwise delay other drivers'
work queued on the shared `events/n` threads.

Core data structures:

- **`struct workqueue_struct`** — represents the whole work-queue system:
  one `cpu_workqueue_struct` per CPU/worker thread, plus metadata (name,
  single-threaded vs. not, real-time, etc).
- **`struct cpu_workqueue_struct`** — per-CPU state: the pending work list,
  a lock protecting it, a wait queue that sleeps the worker thread until
  new work arrives, and pointers to the current work item and owning
  thread.

  ```c
  struct cpu_workqueue_struct {
      spinlock_t lock;              /* lock protecting this structure*/
      struct list_head worklist;    /* list of work */
      wait_queue_head_t more_work;
      struct work_struct *current_struct;
      struct workqueue_struct *wq;  /* associated workqueue_struct */
      task_t *thread;               /* associated thread */
  };
  ```

- **`struct work_struct`** — one queued unit of work: the function to run,
  plus a list entry linking it into the work list.

### Softirqs vs. Tasklets vs. Work Queues

| | Softirq | Tasklet |
|---|---|---|
| **Allocation** | Statically allocated at compile time; can't be dynamically created or destroyed. | Static via `DECLARE_TASKLET(name, func, data)`, or dynamic via `tasklet_init(name, func, data)`. |
| **Concurrency** | Reentrant — even two softirqs of the same type can run concurrently on different CPUs, provided they protect shared state with spinlocks. | Non-reentrant — two tasklets of the *same* type never run concurrently; different types can. |
| **Processing** | Raised via `raise_softirq()`; pending softirqs run via `do_softirq()` / `ksoftirqd`, after being enabled by `local_bh_enable()` or `spin_unlock_bh()`. | Built on softirqs (`HI_SOFTIRQ` / `TASKLET_SOFTIRQ`); `tasklet_schedule()` is effectively `raise_softirq(TASKLET_SOFTIRQ)`. |

The simple rule for choosing: **if the deferred work needs to sleep, use a
work queue; if it doesn't, use a softirq or tasklet.**

| | Context | Can sleep? | Use for |
|---|---|---|---|
| **Work queues** | Process context (kernel thread) | ✅ Yes | Blocking, waiting, or heavy operations |
| **Softirqs / tasklets** | Interrupt (atomic) context | ❌ No | Quick, non-blocking work right after an interrupt |

## Worked Example: A Softirq-Based GPIO Driver

A minimal driver that toggles an output GPIO from a raising-edge interrupt
on an input GPIO, deferring the actual toggle work to a custom softirq
(based on the [EmbeTronicX Raspberry Pi example](https://embetronicx.com/tutorials/linux/device-drivers/softirq-in-linux-kernel/)).
This requires patching the kernel to add a new softirq ID and export the
softirq registration APIs, since drivers can't register new softirq types
against a stock kernel:

The driver itself: the ISR does minimal debounce filtering and immediately
raises the custom softirq; the actual GPIO toggle happens in the softirq
handler, kept separate from the time-critical top half.

```c
/***************************************************************************//**
*  \file       driver.c
*  \details    Simple GPIO driver explanation (Softirq)
*
*              We made the below changes in the linux kernel to support the
*              softirq.
*
*              1. Added EMBETRONICX_SOFT_IRQ in interrupt.h
*              2. Exported the APIs (raise_softirq, raise_softirq_irqoff, open_softirq)
*              3. Compiled the modified kernel and used that
*
*  \author     EmbeTronicX
*  \Tested with Linux raspberrypi 5.10.27-v7l-embetronicx-custom+
*******************************************************************************/
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/module.h>
#include <linux/kdev_t.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/device.h>
#include <linux/delay.h>
#include <linux/uaccess.h>  //copy_to/from_user()
#include <linux/gpio.h>     //GPIO
#include <linux/interrupt.h>
#include <linux/err.h>

/* Raspberry Pi doesn't support hardware GPIO debounce, so this software
** debounce guards against a false double-trigger for a single interrupt.
** Comment out EN_DEBOUNCE if your hardware handles debounce itself.
*/
#define EN_DEBOUNCE

#ifdef EN_DEBOUNCE
#include <linux/jiffies.h>
extern unsigned long volatile jiffies;
unsigned long old_jiffie = 0;
#endif

#define GPIO_21_OUT (21)   // LED output
#define GPIO_25_IN  (25)   // Button input

unsigned int led_toggle = 0;
unsigned int GPIO_irqNumber;

// ISR: fires on the rising edge of GPIO_25_IN. Debounces, then defers the
// actual work to the softirq -- this keeps the top half minimal.
static irqreturn_t gpio_irq_handler(int irq, void *dev_id)
{
#ifdef EN_DEBOUNCE
   unsigned long diff = jiffies - old_jiffie;
   if (diff < 20) {
     return IRQ_HANDLED;
   }
   old_jiffie = jiffies;
#endif
  raise_softirq(EMBETRONICX_SOFT_IRQ);
  return IRQ_HANDLED;
}

// Softirq handler: the deferred bottom-half work -- toggles the LED GPIO.
static void gpio_interrupt_softirq_handler(struct softirq_action *action)
{
  led_toggle = (0x01 ^ led_toggle);
  gpio_set_value(GPIO_21_OUT, led_toggle);
  pr_info("Interrupt Occurred : GPIO_21_OUT : %d ", gpio_get_value(GPIO_21_OUT));
}

dev_t dev = 0;
static struct class *dev_class;
static struct cdev etx_cdev;

static int __init etx_driver_init(void);
static void __exit etx_driver_exit(void);

static int etx_open(struct inode *inode, struct file *file);
static int etx_release(struct inode *inode, struct file *file);
static ssize_t etx_read(struct file *filp, char __user *buf, size_t len, loff_t *off);
static ssize_t etx_write(struct file *filp, const char *buf, size_t len, loff_t *off);

static struct file_operations fops = {
  .owner   = THIS_MODULE,
  .read    = etx_read,
  .write   = etx_write,
  .open    = etx_open,
  .release = etx_release,
};

static int etx_open(struct inode *inode, struct file *file)
{
  pr_info("Device File Opened...!!!\n");
  return 0;
}

static int etx_release(struct inode *inode, struct file *file)
{
  pr_info("Device File Closed...!!!\n");
  return 0;
}

static ssize_t etx_read(struct file *filp, char __user *buf, size_t len, loff_t *off)
{
  uint8_t gpio_state = 0;
  gpio_state = gpio_get_value(GPIO_21_OUT);
  len = 1;
  if (copy_to_user(buf, &gpio_state, len) > 0) {
    pr_err("ERROR: Not all the bytes have been copied to user\n");
  }
  pr_info("Read function : GPIO_21 = %d \n", gpio_state);
  return 0;
}

static ssize_t etx_write(struct file *filp, const char __user *buf, size_t len, loff_t *off)
{
  uint8_t rec_buf[10] = {0};
  if (copy_from_user(rec_buf, buf, len) > 0) {
    pr_err("ERROR: Not all the bytes have been copied from user\n");
  }
  pr_info("Write Function : GPIO_21 Set = %c\n", rec_buf[0]);
  if (rec_buf[0] == '1') {
    gpio_set_value(GPIO_21_OUT, 1);
  } else if (rec_buf[0] == '0') {
    gpio_set_value(GPIO_21_OUT, 0);
  } else {
    pr_err("Unknown command : Please provide either 1 or 0 \n");
  }
  return len;
}

static int __init etx_driver_init(void)
{
  if ((alloc_chrdev_region(&dev, 0, 1, "etx_Dev")) < 0) {
    pr_err("Cannot allocate major number\n");
    goto r_unreg;
  }
  pr_info("Major = %d Minor = %d \n", MAJOR(dev), MINOR(dev));

  cdev_init(&etx_cdev, &fops);

  if ((cdev_add(&etx_cdev, dev, 1)) < 0) {
    pr_err("Cannot add the device to the system\n");
    goto r_del;
  }

  if (IS_ERR(dev_class = class_create(THIS_MODULE, "etx_class"))) {
    pr_err("Cannot create the struct class\n");
    goto r_class;
  }

  if (IS_ERR(device_create(dev_class, NULL, dev, NULL, "etx_device"))) {
    pr_err("Cannot create the Device \n");
    goto r_device;
  }

  if (gpio_is_valid(GPIO_21_OUT) == false) {
    pr_err("GPIO %d is not valid\n", GPIO_21_OUT);
    goto r_device;
  }
  if (gpio_request(GPIO_21_OUT, "GPIO_21_OUT") < 0) {
    pr_err("ERROR: GPIO %d request\n", GPIO_21_OUT);
    goto r_gpio_out;
  }
  gpio_direction_output(GPIO_21_OUT, 0);

  if (gpio_is_valid(GPIO_25_IN) == false) {
    pr_err("GPIO %d is not valid\n", GPIO_25_IN);
    goto r_gpio_in;
  }
  if (gpio_request(GPIO_25_IN, "GPIO_25_IN") < 0) {
    pr_err("ERROR: GPIO %d request\n", GPIO_25_IN);
    goto r_gpio_in;
  }
  gpio_direction_input(GPIO_25_IN);

#ifndef EN_DEBOUNCE
  // gpio_set_debounce isn't supported on the Raspberry Pi -- EN_DEBOUNCE
  // above handles it in software instead.
  if (gpio_set_debounce(GPIO_25_IN, 200) < 0) {
    pr_err("ERROR: gpio_set_debounce - %d\n", GPIO_25_IN);
  }
#endif

  GPIO_irqNumber = gpio_to_irq(GPIO_25_IN);
  pr_info("GPIO_irqNumber = %d\n", GPIO_irqNumber);

  if (request_irq(GPIO_irqNumber, (void *)gpio_irq_handler,
                  IRQF_TRIGGER_RISING, "etx_device", NULL)) {
    pr_err("my_device: cannot register IRQ ");
    goto r_gpio_in;
  }

  // Wire our softirq handler to the custom softirq ID added above.
  open_softirq(EMBETRONICX_SOFT_IRQ, gpio_interrupt_softirq_handler);

  pr_info("Device Driver Insert...Done!!!\n");
  return 0;

r_gpio_in:
  gpio_free(GPIO_25_IN);
r_gpio_out:
  gpio_free(GPIO_21_OUT);
r_device:
  device_destroy(dev_class, dev);
r_class:
  class_destroy(dev_class);
r_del:
  cdev_del(&etx_cdev);
r_unreg:
  unregister_chrdev_region(dev, 1);
  return -1;
}

static void __exit etx_driver_exit(void)
{
  free_irq(GPIO_irqNumber, NULL);
  gpio_free(GPIO_25_IN);
  gpio_free(GPIO_21_OUT);
  device_destroy(dev_class, dev);
  class_destroy(dev_class);
  cdev_del(&etx_cdev);
  unregister_chrdev_region(dev, 1);
  pr_info("Device Driver Remove...Done!!\n");
}

module_init(etx_driver_init);
module_exit(etx_driver_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("EmbeTronicX <embetronicx@gmail.com>");
MODULE_DESCRIPTION("A simple device driver - SoftIRQ (GPIO Interrupt) ");
MODULE_VERSION("1.42");
```
